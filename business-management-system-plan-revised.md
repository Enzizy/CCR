# Business Management System — Product & UI Plan

## Purpose

Build a simple internal business management system for tracking the company's purchase orders, deliveries, statements of account, payments, business expenses, and monthly financial performance.

This document is a **product/design plan, not a rigid implementation task list**.

The implementation decisions should be made by Codex/the implementation model after inspecting the existing project, its stack, conventions, dependencies, and structure.

The goal is to give the implementation model the business context, desired behavior, design principles, and boundaries, then let it flesh out the best architecture and implementation.

---

# 1. Critical First Phase: UI First

**Build the UI/UX first before implementing the backend, database, AI integration, or business logic.**

Start by understanding the existing project and then design the complete application interface.

The first phase should establish:

- application shell
- navigation
- dashboard
- PO screens
- delivery screens
- delivery-trip screens
- DR preview/print experience
- SOA screens
- payment screens
- expense screens
- employee/salary/cash-advance screens
- reports
- settings
- AI assistant interface

Use realistic mock data so the complete workflows can be experienced before the data layer is implemented.

The UI should feel like a real internal business application from the beginning, not a collection of disconnected mockup pages.

After the UI direction is established and coherent, determine the appropriate backend/database implementation.

Do not prematurely lock the architecture merely because this document mentions possible concepts. Inspect the project first and make the best technical decisions.

---

# 2. Design Direction

The design should be:

- simple
- professional
- practical
- information-dense without feeling cluttered
- easy for non-technical business users
- fast to understand
- easy to operate repeatedly
- suitable for printing documents
- visually restrained

## Avoid AI slop

Do NOT automatically fall into generic AI/SaaS dashboard patterns.

Avoid:

- excessive rounded cards
- excessive pill-shaped UI
- gradients used only for decoration
- glowing effects
- glassmorphism
- huge hero sections
- oversized decorative icons
- unnecessary illustrations
- excessive badges
- nested cards
- cards inside cards inside cards
- excessive shadows
- arbitrary colored status chips everywhere
- giant dashboard numbers with meaningless decoration
- redundant subtitles
- repetitive explanatory text
- unnecessary animations
- excessive whitespace that makes business information harder to scan
- generic purple/blue "AI" aesthetics
- unnecessary charts
- decorative UI that does not communicate information

Prefer:

- strong typography
- clear hierarchy
- tables where tables make sense
- whitespace used intentionally
- simple borders/dividers
- restrained use of color
- clear forms
- predictable interactions
- compact but readable layouts
- functional navigation
- obvious actions
- sensible empty states
- real-world document layouts

The application should look like a thoughtfully designed business tool, not a template generated by an AI UI generator.

- agreed/unit price

# 8. Partial Deliveries

Partial delivery is a normal business workflow, not an exception.

The UI should make it very easy to see:

- ordered
- delivered
- remaining

The system should prevent accidental over-delivery where appropriate while still allowing the implementation model to design a sensible override/exception workflow.

The user should never have to manually calculate remaining quantities.

# 10. DR Numbering

DR numbers must be controlled by the system.

The numbering scheme should be configurable based on the company's existing practice.

Do not assume a specific numbering format if the existing project or company documents reveal another convention.

# 11. Replacement Deliveries

Sometimes delivered items are damaged.

The company then delivers replacement items and provides another DR.

Replacement deliveries must be first-class functionality.

Example:

Original:

DR #4322

- 50 Solid Panel Doors

Customer reports:

- 2 damaged doors

Replacement:

DR #4331

- 2 Solid Panel Doors

The replacement DR should:

- identify itself as a replacement
- reference the original DR
- record the reason
- contain the replacement items
- not incorrectly increase the PO fulfillment quantity
- not create additional revenue when it is a free replacement
- remain part of the delivery history

This distinction is important:

Physical units delivered can include replacement units, while PO fulfillment should represent actual fulfillment of the ordered quantity.

The UI should make this understandable without requiring the user to understand accounting terminology.

# 13. Delivery Trips

A physical delivery trip can contain deliveries for multiple customers.

Do NOT assume:

`One delivery trip = one customer`.

Example:

Delivery Trip:

- DR #4322 → Cebu Landmaster Inc.
- DR #4323 → Shalom Constructions Inc.

One truck can carry products for both customers.

Therefore, model the physical trip separately from the customer-specific DRs.

A delivery trip may contain:

- date
- vehicle
- driver
- multiple DRs
- trip expenses
- notes

This is also where automatic gas/fuel expense creation becomes useful.

---

# 14. Automatic Trip Expenses

When recording a delivery trip, the user may enter expenses such as:

- Gas
- Toll
- Parking
- Other trip costs

Example:

Delivery Trip #2026-0092

Gas:

`₱2,500`

When the trip is saved, the system should automatically create/refelect the corresponding business expense.

The user should NOT need to enter the ₱2,500 again in the Expenses module.

Example:

Delivery Trip:

`Gas = ₱2,500`

Automatically becomes:

Expense:

- Category: Gas/Fuel
- Amount: ₱2,500
- Date: trip date
- Reference: Delivery Trip #2026-0092

This expense is a **general business expense**.

It does not need to be allocated between Cebu Landmaster Inc. and Shalom Constructions Inc. even if the trip serves both customers.

The same general principle can apply to other workflows where an operational activity naturally creates a business expense.

The primary goal is to understand total business expenses.

# 27. Important Financial Distinction

Do not calculate financial truth by asking Gemini to perform arithmetic.

The application/database should calculate:

- totals
- balances
- revenue
- expenses
- receivables
- payments
- profit
- cash flow

AI should retrieve and explain these values.

Architecture concept:

```text
User
 ↓
AI
 ↓
Application function
 ↓
Database / business logic
 ↓
Exact result
 ↓
AI explanation
```

The AI should never be the source of truth for financial calculations.

# 32. AI Safety / Architecture

Do not give Gemini direct database access.

Use controlled application functions/tools.

Conceptually:

```text
Gemini
  ↓
Function call
  ↓
Backend
  ↓
Validation / authorization
  ↓
Database
```

The application remains the source of truth.

If Gemini is unavailable, the entire business application must still work normally.

AI should be an enhancement, not a dependency for core operations.

---

# 33. AI Free-Tier Consideration

The initial implementation may use the Gemini API free tier.

However:

- keep the AI integration replaceable
- do not tightly couple the database to Gemini
- isolate AI-related code
- design a provider abstraction if appropriate
- account for API rate limits
- do not assume unlimited free usage

The application should be able to migrate to a paid Gemini tier or another model/provider later without rewriting the entire business system.

# 35. BIR Consideration

Do not assume that a Delivery Receipt is automatically the company's tax invoice.

The application should treat:

- Delivery Receipt
- Statement of Account
- Tax Invoice / other BIR-required sales document

as potentially distinct document concepts.

The exact BIR-compliant document setup should be confirmed with the company's accountant/bookkeeper and current BIR requirements.

The software should be designed so that document types can evolve without restructuring the entire sales system.

Do not hard-code claims about BIR registration/authorization into the application without verified requirements.

# 47. Initial Business Context

Current direct customers:

- Cebu Landmaster Inc.
- Shalom Constructions Inc.

Initial products:

- Door, Wooden Solid Panel 0.90x2.10 m. w/ Jamb Door
- Hollow Core Flush 0.70 x 2.10 m. w/ Jamb

Business model:

1. Customer sends a Purchase Order.
2. Company provides products according to the PO.
3. Products may be delivered completely or partially.
4. A Delivery Receipt is provided for each relevant delivery.
5. A Statement of Account is provided alongside the delivery/billing process.
6. Payment is generally expected within 30 days upon delivery.
7. Multiple deliveries can occur under one PO.
8. Multiple unpaid SOAs can therefore exist for the same customer.
9. Damaged items can require replacement deliveries and replacement DRs.
10. One physical delivery trip can contain deliveries for multiple customers.
11. General business expenses are tracked centrally and totaled monthly.
12. Expenses do not need to be allocated to individual customers/projects.
13. Certain operational activities, such as delivery fuel, should automatically create expense records.
14. Monthly financial performance is the primary financial reporting view.

# 49. Instruction to the implementation model

Treat this document as the **product vision and constraints**.

Do not simply implement every bullet literally.

First inspect the existing codebase and understand its current architecture.

Then use your own judgment to:

- flesh out the product
- identify missing workflows
- identify contradictions
- improve the information architecture
- improve the UX
- determine the appropriate data model
- determine the appropriate technical architecture
- determine the appropriate document-generation approach
- determine the appropriate AI/function-calling architecture
- identify edge cases
- identify accounting/data-integrity risks
- simplify anything unnecessarily complicated

Prioritize the actual business workflow over abstract software patterns.

**Start with the UI.**

Build the UI using realistic mock data first so the complete product can be evaluated visually and interactively before the backend is finalized.

Keep the visual design simple, restrained, professional, and intentionally human-designed.

Use the SOA as the visual reference for color and document identity.

Use anti-generic UI principles as a strong guardrail against generic AI-generated interface patterns.

Do not over-design.

Do not add UI elements simply because they are fashionable.

When something can be communicated clearly with a heading, table, field, or simple action, prefer that over decorative UI.

The final system should feel like a **real internal business tool built for this company's workflow**, not a generic SaaS template.
